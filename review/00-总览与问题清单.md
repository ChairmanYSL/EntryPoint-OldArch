## 一、总体结论

1. **这份快照不可构建，也不可链接。** `src/emv.c` 存在字面语法错误（`int i,j,;`、多余右括号）；源码与头文件处于"半迁移"状态——`EMV_TERMPARAM` 全工程已不存在、`EMV_CONTEXT` 缺 3 个被引用成员、`EMV_CFG_MAX_CANDIDATES` 在 10 个编译单元里不可见；`src/emvapi.c` 还调用 6 个全工程无定义的符号。8 个能生成 `.o` 的文件里，`eTRACE`/`eTRACE_HEX` 是**未定义外部符号**（`nm` 证实），最终链接必然失败。
2. **存在卡可控 / 主机可控的内存破坏。** 卡下发的 SDOL(9F3F) 经 `emvdol_packet` 无界展开写入 262 字节栈缓冲（P0）；主机下发的终端参数/AID 参数经 `conv_param` 越界写（P0）；9F1B 分支 `emv_bcd2hex` 把 12 字节写进 4 字节栈缓冲（P0）；候选列表无容量上限等。
3. **交易主流程有硬缺陷。** 组合选择把所有非接触卡**强制路由到 Mastercard 内核**；内核函数指针未注入且调用处不判空；Entry Point 预处理把 TTQ 的"置位"写成清位（`&=`）；9F29 扩展选择用错下标；在线响应里的 71/72 发卡行脚本必然落库失败/写错位置；CAPK 完整性校验被注释掉。
4. **结论：这是一个半迁移中的工作副本，不是可送检/可交付状态。** 建议先"恢复可构建 + 修复 P0 内存破坏"，再按 P1 修交易主流程，最后做规范/认证项与工程化（编码、版本、构建可复现）。在此状态下发认证测试，任何"交易失败/异常"都无法区分是内核缺陷还是构建问题。

### [P0] E-1 源码语法错误，`emv.c` 无法编译（等同模块 B P0-1）

```c

{
    EMV_AIDPARAM  aid_param={0};
    int i,j,;                                   /* emv.c:1155 */
...

```

### [P1] E-4 `emvdbg.h` 的调试宏本身是坏的，调试开关也失效

- 位置：`src/inc/emvdbg.h:26-41`
- 证据：

```c
#if (defined KS_DEBUG) || (EMV_CFG_DEBUG == ENABLE)
#define eTRACE(fmt,...) API_Trace(0x01, "...", __FUNCTION__, __LINE__, ##__VA_ARGS__)
#define eTRACE_HEX(msg, hex, hexlen) \
        API_TraceHex(0x01, (msg), (hex), (hexlen)).      /* ← 末尾多一个 '.' */
```

  - 该 `.` 使 `eTRACE_HEX(...)` 展开后变成非法表达式；用 gcc 最小复现可复现编译错误。当前没暴露，是因为**唯一包含 `emvdbg.h` 的 3 个 TU 恰好都没调用 `eTRACE_HEX`**（见 E-3 表格），一旦在这些文件里用一次就编译失败。
  - `EMV_CFG_DEBUG` 被定义成 `ENABLE`（`emvdbg.h:18`）。`ENABLE` 在 `emvi.h:43` 定义为 1：`1 == 1` 恒真；若 `ENABLE` 尚未定义（`emvdbg.h` 先于 `emvi.h` 被包含），预处理器把两侧都当 0，`0 == 0` 仍恒真。**`EMV_CFG_DEBUG` 这个开关实际上关不掉调试日志**，与 `NDEBUG` 无关。
- 影响：发布库默认带全量调试输出（数百处 `API_Trace` 调用，串口/日志开销、可能泄露 TLV/PAN 数据）；宏本身是定时炸弹。
- 建议：删掉多余的 `.`；改用 `#if (EMV_CFG_DEBUG == ENABLE)` 并保证 `ENABLE` 已定义（或直接 `#if EMV_CFG_DEBUG_LEVEL >= 1`）；`EMV_CFG_MAX_CANDIDATES` 这类业务常量从 `emvdbg.h` 移到 `emvi.h/emv_type.h`。

### [P2] E-6 缓冲容量契约不符（文档 7168/9216 vs 实际 ≥11.2KB）

- 位置：`src/inc/emv.h:192`（注释"建议开 7168 字节以上"）、`inc/emvapi.h:218,226`（"7168"与"9216"两种说法）、`src/emv.c:994,1036`、`src/emvspi.c:895-904`

## 四、P0 运行期缺陷（去重后 6 条）

> 编号沿用模块报告；每条均可从源码直接复核，不依赖构建能否通过。

### P0-1 卡下发的 SDOL(9F3F) 经 `emvdol_packet` 无界展开，栈溢出（卡可控）
- 位置：`src/emvtlv.c:1541-1632`（根因）、`src/emv_application_selection.c:361-429`（调用方，`pack[262]`，`emvi.h:45` 定义 262）
- 证据：`emvdol_packet` 的 `val_max_len` 只在开头 `emv_memset` 里用过一次；循环中 `val_len += reqlen`，写 `val + val_len` 前从不比较 `val_len + reqlen <= val_max_len`；`reqlen` 直接取 DOL 里的长度字节（≤255/项）。`sdol_process` 用 `uint8_t pack[EMV_CFG_ICC_SEND_MAXLEN]`（262）接收，SDOL 由卡在 PPSE FCI 的 9F3F 提供（`deal_ppse_resp` 884-887 行入库）。
- 影响：一张恶意/异常卡可让 SDOL 含数十项、每项 255 字节，向 262 字节栈缓冲写入上万字节 → 覆盖返回地址/相邻局部变量，卡侧触发的栈溢出（终端侧 RCE/崩溃）。
- 建议：`emvdol_packet` 内每项写入前校验剩余容量并返回错误；`sdol_process` 对 `pack_len` 与 `sizeof(pack)` 做"写入前"校验；补恶意 SDOL 的负例测试。

### P0-2 主机下发的终端参数/AID 参数经 `conv_param` 越界写
- 位置：`src/emvporting.c:292-651`（`conv_param`），关键 `325/331/337/343/434/597/604/628/634`
- 证据：对 9F01/9F1E/9F15/9F16/9F06/9F33/9F40/DF8124/DF8125 等只判断 `tlvs[i].valuelen` 非零就 `API_memcpy` 到定长字段；`emv_set_termparam/emv_add_aidparam` 落盘前不校验字段长度，`EMV_PreProcess` 在栈上用 `EMV_AIDPARAM`。
- 影响：主机/参数文件下发的超长值可在 `EMV_PreProcess` 的栈帧上写越界约 1KB（参数来源是"外部不可信输入"）。
- 建议：按 `sizeof(目标字段)` 逐字段校验；超长拒绝并记录错误；`conv_param` 的每个 tag 分支统一走"长度白名单"。

### P0-3 9F1B 六字节分支 `emv_bcd2hex` 把 12 字节写进 4 字节栈缓冲
- 位置：`src/emvporting.c:296`（`unsigned char term_floor_lmt[4]`）、`src/emvporting.c:564-565`、`src/emv.c:439-467`
- 证据：`emv_bcd2hex` 对每个 BCD 字节输出 2 字节（`hex_data[2*i]/[2*i+1]`），`valuelen==6` 时写 12 字节到 `term_floor_lmt[4]`；随后只按 `sizeof(apar->term_floor_limit)` 拷贝——既溢出又把 floor limit 值算错。
- 影响：固定 8 字节栈越界（参数可控），且终端 floor limit 被算错 → 交易限额判断错误。
- 建议：按"BCD 字节数 → 定长二进制"的正确转换重写该分支，缓冲按目标字段大小声明并校验。

### P0-4 `icccommand` 成功但响应为空时不回写 `*outlen`，调用方用未初始化长度
- 位置：`src/emvicc.c:350-360`；调用方 `src/emv.c:1660,1694,1717,1726`、`src/emv_application_selection.c:368,520,533`、`src/emvbuf.c:455-461`

- 影响：卡侧可控的越界读/写（长度来自栈垃圾）。
- 建议：入口就把 `*outlen` 置 0；`rlen==0` 时明确返回"无数据"错误码；调用方一律初始化长度变量。

## 五、P1 清单（20 条 = 18 条模块 P1 + 构建面 E-4/E-5）

> `EMV_TLV_PacketByTAG` 由模块 B 的 P0-4 降级并入第 10 条；E-4（调试宏/开关失效）、E-5（构建不可复现）见第三章。

### 5.1 Entry Point 流程与规范（A/B）
1. **组合选择把所有非接触卡强制路由到 Mastercard**：`src/emv_combination_Selection.c:123` 无条件 `g_emv_cnxt->contactless_type = EMV_CONTACTLESSTYPE_QMSDC;`，前面 120 行的 Visa/Amex/JCB/Discover/PBOC/PURE 识别全部被覆盖为死逻辑。→ 非 MC 卡（Visa payWave、PBOC 等）会进 PayPass 内核处理，交易结果不可信。
2. **内核函数指针未注入且调用处不判空**：`src/emv_selec_kernel.c:22-34`（contact 分支 `contact_process` 赋值被注释，仅 return EMV_OK）、`:39-71`（QPBOC/QVSDC/JCB/AMEX/DISV/QPURE 分支空转，只有 QMSDC 在 `:60` 赋值）；`src/emv.c:1403,1407` 无条件 `emv_k_interface.emv_process()`（全局零初始化）。叠加 `emv.c:1170-1171` 的 `card_types_allowed` 只置 CONTACTLESS，接触式在 `EMV_SetCardType` 即被拒。→ 触点能力实际不存在；若产品要求触点交易则升 P0。
3. **Entry Point 预处理 TTQ 用 `&=` 清位而非 `|=` 置位**：`src/emv.c:1200,1279,1284,1291,1301`。多步叠加会把 TTQ Byte2 逐步清空，下游内核的"是否联机/CVM/ODA"决策被破坏。
4. **9F29 扩展选择用错下标 + PPSE 主路径未处理**：`src/emv_application_selection.c:226`（`termapps[i]` 应为 `termapps[j]`，越界读终端应用表）；`deal_ppse_resp` 全流程没有 9F29 处理（只有 SPI 路径有）。
5. **`resp_len`/`rlen` 未初始化**：`src/emv_application_selection.c:368`、`:1270`（`select_ddf`）。卡返回 9000 但无数据时按栈垃圾长度解析（与 P0-4 同源）。
6. **`sdol_process` flag=3 追加容量判断偏小**：`src/emv_application_selection.c`（追加 5 字节却按 `poi_len+3` 判断）→ `pack_len=258` 时 1 字节栈越界 + `pack[1]` 长度字节回绕。
7. **在线响应 71/72 发卡行脚本必然丢失/写错**：`src/emv.c:1530-1556` 把 71/72 改名为 `0xDF8100/0xDF8200` 递增后存表；`0xDF8100` 不在标签库（`emvtag.c` 252 项中无此值）→ 静默丢弃；`0xDF8101` 已被 DS Summary2 占用 → 要么长度不符被拒、要么覆盖数据认证摘要。`appdata_save_tlv` 返回值未检查。
8. **`EMV_TLV_PacketByDOL` 把错误当成功**：`src/emv.c:1880-1897`，失败时写 `*pOutLen=-1` 却返回 `EMV_OK`，调用方按长度 -1 去 `memcpy` 即超大拷贝。
9. **`EMV_ResultSelCandidates` 不校验 index**：`src/emv.c:1421`，消费方 `src/emvapi.c:303`、`src/emv_combination_Selection.c:37` 直接用该值索引 `candidates[12]` → 越界读，`emv_get_kernel_id` 还会按越界读到的长度再拷贝到调用方缓冲。
10. **`EMV_TLV_PacketByTAG` 先写后查**：`src/emv.c:1921-1933`（见第四章附注）。

### 5.2 数据层（C）
11. **`emvdol_packet_tlv` 先写后查**：`src/emvtlv.c:1756-1784`（公共 API `EMV_TLV_PacketByDOL`），输出缓冲越界写、输入越界读；0x84 四字节长度条目可让 `reqlen` 为负 → `memcpy` 巨值。

### 5.3 移植层与持久化（D）
14. **`emvporting_get_termapps` 无条目上限**：`src/emvporting.c:1143-1245`，`while(1)` 逐条追加直到文件尾，AID 文件 50~90 条即可写出 `emv.c` 划给 termapps 的区域（内核 14KB 静态缓冲），并破坏相邻全局。

16. **`EMV_FNAME` 的 `_PARAM` 分支缺失、`kernel_index` 恒 0**：`src/emvporting.c:109-178`，`apipara_init` 恒失败 → TSC/内核索引不持久化、多内核共用 `*0.par`、并对 SDK 传 `NULL` 文件名。

### 5.4 ICC/SPI（E）
17. **全层无 61xx/6Cxx 处理**：`src/emvicc.c:295-362`、`src/emvspi.c:920-940` 直接透传 SDK 返回值；工程内检索无 `0x61/0x6C`、GET RESPONSE 代码。需与 SDK/驱动方确认是否代劳；若确认代劳则降 P2/P3。
18. **`get_random` 不校验长度、忽略 `API_Rng` 失败且恒返回 0**：`src/emvspi.c:1042-1058`（`uint8_t buf1[256]`，`len>256` 即栈溢出）——内核若传大长度即内存破坏。
> 另：调试日志默认全开与输出宏缺陷见 **E-4**（第三章，已计入 P1）；APDU 敏感数据掩码被整段注释为 P3（`src/emvicc.c:245-342`，`EMV_APDU_DEBUG` 一旦开启将明文记录 PAN/二磁道），不计入本 P1 清单。

## 六、P2/P3 概括（47 + 28 条，详见模块报告）

- **outcome / UIRequest（B）**：PresentFlag 置位与实际 TLV 表内容不一致（Data Record/Discretionary Data）；`EMV_SetUIRequest` 的 value qualifier/value/currency 参数被整段注释（L3 拿不到余额等展示数据）；`outcome_seephone` 同一事件用了两种 UI type；`JNISend*` 无声明无定义，链接依赖外部符号。
- **API 语义（B）**：`emv_process2` 只覆盖部分状态（25~59、100~117 大量状态落到 `STATUS_ERROR 255`）；`emv_process` 不消费 `g_emvapi_messageinx`；`emv_get_version` 无长度参数、IDLE 下取不到版本仍返回 OK；`emv_set_card_type` 缺 `return`；`emv_get_kernel_id` 无 NULL/边界校验；对外读取 API 全都没有输出容量参数。
- **数据层（C）**：`EMV_GetTransLog/EMV_GetLoadLog` 用 256 字节栈缓冲接收卡记录（长度由卡控制）；`emvtlv_decode_itemlist`/`OutputTLV`/`GetTagFromList`/`add_tlv_*` 一族为对外导出但当前无调用点，按集成方使用后果定级并已注明可达性。
- **移植层（D）**：`transwater` 的长度/文件内 `length` 未校验直接进 `API_fread/fwrite`（u32 计数）；`checkCAPKhash` 逻辑与注释不符；DRL/黑名单容量与下标边界。
- **ICC/SPI（E）**：`emvicc_put_data` 响应缓冲仅 4 字节（卡返回数据即越界写）；`recover` 只实现 RSA（SM2/ECC 直接 -1；若产品要求 PBOC2018 国密则升 P1）；`icc_rw` 未知类型静默返回 0x0000；ICC 层无输出容量契约；`EMVSPI_DO=1` 分支不可编译且其中 PIN/选应用实现有多处越界（一旦启用即 P0）；`icccommand` 把 ≤512 字节 `recv` 直接拷给调用方 `output`。
- **规范/工具（B/E）**：`emv_date_compare` 世纪硬编码 `0x20`（1999 年过期卡被判 2099 年有效，当前无调用点）；`emv_hex2dec` 移位越界、`emv_memcmp` 负长度视为相等；9F41 计数器回绕、日期时间无有效性校验；APDU 构造函数 `int32_t` 长度静默截断为 `uint8_t` Lc。
- **工程卫生**：E-8（无版本控制/README、中间产物入库、版本号三套不一致、两套 API 头文件并存）。

## 七、跨模块 / 架构观察

1. **两套对外 API + 一套内核接口并存**：`inc/emvapi.h`（`emv_*` 旧层，返回 `STATUS_*`/`EMV_*` 消息）与 `src/inc/emv.h`（`EMV_*` 新层，返回 `EMV_STA_*` 状态码），中间由 `emvapi.c` 做薄封装；两层的错误码/状态语义没有统一文档，`emvapi.c` 的映射已不完整。建议二选一或明确"哪层是稳定 ABI"。
2. **Entry Point ↔ 内核的边界是"一个函数指针"**：`emv_k_interface.emv_process` 由 `emv_selec_kernel.c` 按 `contactless_type` 赋值，外部 PayPass/Contact 内核库不在本工程内（`include/paypass_api.h`、`include/contact_api.h` 只有声明，无库文件/链接说明）。这层边界没有版本号、能力协商、NULL 防护，是本次 P0/P1 的集中来源。
3. **回调契约"文档一套、实现一套"**：`emv.h` 文档描述回调直接返回 UI 选择结果（0..count-1 等），而本构建 `EMVSPI_DO=0`，除 `message()` 外全部返回 `EMV_OPER_REPORT_APP`，依赖 L3 用 `EMV_Result*` 回填。头文件没有说明当前走 report-app 模式，集成方极易用错（也解释了 `emv.h` 里大量"支持/不支持"的含糊表述）。
4. **outcome 与规范一致性**：`outcome_*` 先发 UIRequest 再发 Outcome、PresentFlag 位序（b8→b5、b4）与 Entry Point Book B 基本一致（未逐字比对 PDF），但"置位后没写数据"、"seephone 的 UI type 不确定"、`OUTCOME_START_NA=0xF0` 是否被 L3 认可需要与规范/L3 对齐。
5. **认证相关不可静态确认项**：`emv_ics.h` 的 ICS 默认值由外部 `ics_option()` 提供（本工程无定义），SPI、持卡人确认、PIN bypass 等路径是否默认开启无法静态判定；本报告对依赖 SPI 的 P0/P1 已标注该前提。
